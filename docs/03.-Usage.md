## Usage

TabbyAPI's main use-case is to be an API server for running ExllamaV3 models.

### API Server

Currently TabbyAPI supports clients that use the [OpenAI](https://platform.openai.com/docs/api-reference) standard and [KoboldAI](https://lite.koboldai.net/koboldcpp_api)'s API.

In addition, there are expanded parameters to generation endpoints along with administrative endpoints for loading, unloading, loras, sampling overrides, etc.

> [!NOTE]
> If you are a developer and want to add full TabbyAPI support to your app, it's recommended to use the [autogenerated documentation](https://theroyallab.github.io/tabbyAPI).

TabbyAPI also answers the discovery endpoints that clients written for llama.cpp's `llama-server` use to detect a local model's capabilities, so tools such as coding agents can pick up the context size, vision support and thinking support without manual configuration:

- `GET /props` returns `model_path`, `default_generation_settings.n_ctx`, `total_slots`, `chat_template` and `modalities.vision` for the loaded model.
- `GET /v1/models` entries carry a `meta` block with `n_ctx_train`, `n_vocab` and `n_embd` read from the model's `config.json`; the loaded model additionally reports `n_ctx` and the weight `size` in bytes.
- `POST /apply-template` (also `/v1/apply-template`) renders chat messages through the prompt template and returns `{"prompt": ...}` without generating.
- Messages with the OpenAI `developer` role are treated as `system` messages.
- `return_progress: true` on a streaming `/v1/chat/completions` or `/v1/completions` request adds chunks during prompt processing that carry a top-level `prompt_progress` object (`total`, `cache`, `processed`, `time_ms`, as in llama.cpp), one per prefill chunk, so a client can show progress on a long prompt instead of waiting silently for the first token.

Completion and chat completion responses also carry a llama.cpp-style `timings` object (prompt/generation times and rates, cache and draft counters) for clients that read it off llama-server: top-level on non-streaming responses, on the final chunk of a stream (the usage chunk when `stream_options.include_usage` is set), and only for requests that produce a single generation.

Below is an example CURL request using the OpenAI completions endpoint:

```bash
curl http://localhost:5000/v1/completions \
-H "Content-Type: application/json" \
-d '{
  "model": "Meta-Llama-3-8B-exl3",
  "prompt": "Once upon a time,",
  "max_tokens": 400,
  "stream": false,
  "min_p": 0.05,
  "repetition_penalty": 1.05
}'
```

### Chat client

TabbyAPI serves a small chat client at `http://<host>:<port>/ui` for trying out models and settings without a separate frontend. It can:

- Load and unload models from the model directory. Picking a model fills in the load options that would apply to it (from its `tabby_config.yml` and config.yml's `use_as_default`) as YAML, which you can edit before loading; edits override the file. A model outside the list can be loaded by typing its path into the filter box. Star models to keep them at the top of the list.
- Set every sampling parameter the server supports. Parameters left unset aren't sent, so the server's sampler overrides apply, and the panel shows those values as the defaults. The server-wide override preset can also be switched from there.
- Show reasoning separately from the answer, with token counts and speeds for each response.
- Attach images by pasting them, dropping them on the page or with the paperclip button, for models loaded with vision. PNG, JPEG, WebP, GIF and BMP files up to 20 MB and 50 megapixels are accepted.
- Format replies as Markdown (headings, lists, tables, code blocks, links), or show them as the exact text the model wrote. HTML in a reply is always shown as text, and images are only shown when embedded in the reply; others become links. Code blocks have a copy button, and SVG code gets a preview of the graphic below it, drawn as an image so it can't run scripts or load anything.

Chats and settings are kept in the browser's local storage, and attached images in its IndexedDB storage, so they persist across server restarts but belong to that browser. At startup the server prints a link to the client with the admin key in it (after a `#`, so the browser never sends it to the server); opening that link logs the client in. Otherwise the client asks for a key on first use; use the admin key to list and load models. The client can also be pointed at another TabbyAPI instance from its connection settings, as long as that server's `allowed_origins` permits it.

Set `web_ui: false` in the network section of `config.yml` to turn it off.

### Authentication

Every call to a TabbyAPI endpoint requires some form of authentication. Keys have two types of permissions:
- API: Accesses non-invasive endpoints (ex. generation, model list fetching)
- Admin: Allowed to access protected endpoints that deal with resources (ex. loading, unloading)

In addition, when calling list endpoints, API keys will only fetch the currently loaded object while admin keys will list the entire directory. For example, calling /v1/models will return a list of the user-configured models directory only if an admin key is passed.

Therefore, it's recommended to keep the admin key for yourself and only share the api key with users.

If these keys get compromised, shut down your server, delete the api_tokens.yml file, and restart. This will generate new keys which you can share with users.

To bypass authentication checks, set disable_auth to True in config.yml. However, turning off authentication without a third-party solution will make your instance open to the world.

### Chat request debug logs

For bug-report reproduction, TabbyAPI can write every `/v1/chat/completions` request to a JSON file in `logs/debug`. Enable it in `config.yml`:

```yml
logging:
  log_chat_completion_requests: true
```

> [!WARNING]
> This creates a comprehensive request log. Each file includes the full message history and generation parameters. API keys are redacted, but prompts and user-provided content are preserved.

Inspect a saved request before sharing it:

```bash
python tools/inspect_chat_request.py logs/debug/<request>.json
```

Replay a saved request against a running TabbyAPI server and stream the raw response to the console:

```bash
python tools/replay_chat_request.py logs/debug/<request>.json --api-key <api key>
```

### Model loading

> [!IMPORTANT]
> All loading methods require an admin key.

TabbyAPI has a set of endpoints used for model loading and unloading:
- `/v1/model/load`: Loads a model from the configured model_dir with the provided parameters. If the provided model name is different than the currently loaded model, the existing model will be unloaded beforehand.
- `/v1/model/unload`: Unloads all model tensors and terminates all pending generation requests. Only use this endpoint in an emergency or if you want to free VRAM but leave the server running.
- `GET /v1/model/load_config?model_name=...`: Shows the options a load of that model would use for anything the request leaves out: the model folder's `tabby_config.yml` over the `use_as_default` keys of config.yml. The response has them as a JSON object (`settings`, with draft options under `draft_model`), with the source of each (`sources`), and as annotated YAML (`yaml`) that can be edited and sent back as a load request.
- `POST /v1/model/load_config/parse`: Turns load options written as YAML (`{"yaml": "..."}`) into a JSON load request body, for clients that let users edit them as YAML.

The model list (`/v1/models` with an admin key) searches up to four folders deep, so quant-style layouts such as `<model>/exl3/4.0bpw` are listed by their path under `model_dir`, the same name `/v1/model/load` takes. A folder counts as a model when its `config.json` names the model architecture (`architectures`), and folders inside a model aren't searched.

Load settings are applied in this order, later ones winning: `use_as_default` keys from config.yml, the model folder's `tabby_config.yml`, then the options set in the load request.

Please note that load requests are ephemeral and `config.yml` options will not apply. If you want to apply options from your config as fallback defaults, add them in the `use_as_default` key under model options.

Below is an example CURL request using the model load endpoint:

```bash
curl http://localhost:5000/v1/model/load \
-H "Content-Type: application/json" \
-d '{
  "model_name": "Meta-Llama-3-8B-exl3",
  "max_seq_len": 8192,
  "tensor_parallel": true,
  "gpu_split_auto": false,
  "gpu_split": [20, 25],
  "cache_mode": "Q8"
}'
```

A model load request can also include draft model parameters:

```bash
curl http://localhost:5000/v1/model/load \
-H "Content-Type: application/json" \
-d '{
  "model_name": "Meta-Llama-3-8B-exl3",
  ... Other parameters
  "draft_model": {
	draft_model_name: "TinyLlama-1B-32k-exl3",
	draft_rope_scale: 1.0
  }
}'
```

For more information on what parameters can be passed, please look at the [autogenerated documentation](https://theroyallab.github.io/tabbyAPI/#operation/load_model_v1_model_load_post)

### Inline loading

> [!NOTE]
> If you want more fine-grained customization when loading, it's highly recommended to use the traditional endpoints instead. Inline loading is an alternative method  that doesn't allow parameters to be passed on request.

An alternative way of switching models is called "inline loading" which hooks into the model switching logic used by frontends such as OpenWebUI. As previously stated, model requests are ephemeral, so there needs to be a way to provide per-model defaults while also being explicit to the admin user. This is where `tabby_config.yml` comes into play.

To get started, set `inline_model_loading` to `true` under the model block of config.yml.

Now to create a tabby config, let's say we have a model in our models directory called `Meta-Llama-3-8B-exl3`. Navigate into that model folder and create a file called `tabby_config.yml`

Now, you can place any model load parameter from `/v1/model/load` into that file. Settings from `tabby_config.yml` override the startup config.yml values and the `use_as_default` keys. A `/v1/model/load` request overrides the file for the options it sets, so you can try different settings without editing it. Here's a simple example which changes the default `max_seq_len` to 8192 and sets a Q6 quantized cache:

```yml
model:
  max_seq_len: 8192
  cache_mode: Q6
```

If you'd like to provide draft model options, you can add them under the `draft_model` key:

```yml
model:
  max_seq_len: 8192
  cache_mode: Q6
draft_model:
	draft_model_name: TinyLlama-1B-32k-exl3
	draft_rope_scale: 1.0
```

To switch the currently loaded model, send a request to `/v1/completions` or `/v1/chat/completions` with the `model` parameter set to the desired folder.

Inline loading is strict: a request that names a model which doesn't exist in the model directory gets a `404`, and one whose model fails to load gets a `503`, rather than being answered by whatever model is currently loaded. Model names listed under `dummy_model_names` (with `use_dummy_models` on) are the exception and run on the loaded model, for clients that always send a name such as `gpt-3.5-turbo`.

Below is an example CURL request for inline loading:

```bash
curl http://localhost:5000/v1/completions \
-H "Content-Type: application/json" \
-d '{
  "model": "Meta-Llama-3-8B-exl3"
  ... Other parameters
}'
```

This will unload the existing model and load the new model with defaults specified from `tabby_config.yml`

### Difficult to get started?

Is the API difficult? Don't want to load models with config.yml? That's okay! Not everyone is a master user of AI products when starting out. 

For newer users, it's recommended to use a UI that allows for managing TabbyAPI via API endpoints.

To find UI projects, take a look at [Community Projects](https://github.com/theroyallab/tabbyAPI/wiki/09.-Community-Projects) for more information.

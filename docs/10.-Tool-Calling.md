# Tool Calling in TabbyAPI   

Tool calling is available for supported models, and enabled by selecting a tool format in the model 
config. This can also be specifed per model using `tabby_config.yml`.  

Most tool-calling models are also reasoning models, and it is recommended to enable reasoning as 
well with appropriate reasoning tags (these cannot currently be inferred from the model's template).
The parser still respects these tags even if the model does not support tool calls or no 
`tool_format` is given.  

```yml
model:
    reasoning: true
    reasoning_start_token: "<think>"
    reasoning_end_token: "</think>"
    tool_format: qwen3_5
```

### Supported formats

Below are the currently recognized tool call formats.

By default `tool_format` is `auto`: when a model loads, TabbyAPI scores every format against the
model's chat template (the literal markers it renders around a tool call), the special tokens in
its tokenizer and, as a tie-break, its architecture, and selects the unique best match. The
reasoning tags default to `auto` as well and are taken from the detected format when the template
or tokenizer confirms them, otherwise from the template alone; if none are found, reasoning parsing
is switched off for that model. The startup log reports the outcome on a `Response parsing:` line.
When no format matches a template that does define tools, the server warns and tool calls are not
parsed; set `tool_format`, `reasoning_start_token` and `reasoning_end_token` explicitly in
config.yml or the model folder's `tabby_config.yml` in that case. Setting any of them explicitly
always overrides detection.

**¹** Older Mistral models tend to have unreliable tool calling support and even newer ones are 
often released without official chat templates or with templates that omit any tool formatting. 
Tokenization also changes frequently between model releases. YMMV

**²** The Harmony format (gpt-oss) and the Muse Glimmer format structure the whole response —
reasoning, content and tool calls — as structured messages (channels in Harmony, recipients in
Glimmer). Both are detected automatically from the model's special tokens and need no
configuration; `tool_format: harmony` / `tool_format: muse_glimmer` are also accepted and are
equivalent to setting `harmony: true` / `muse_glimmer: true` in the model config. When active they
supersede the `reasoning` and `tool_format` settings. Set `harmony: false` / `muse_glimmer: false`
to override the detection.

**³** Note that Hy3's standard chat template disables reasoning by default and does not respect
`enable_thinking`. Clients can enable reasoning per request with the top-level `reasoning_effort`
field or `chat_template_kwargs: {"reasoning_effort": "high"}` (options: `no_think`, `low`, `high`).
To enable reasoning by default server-side, set `template_vars_default: {reasoning_effort: high}` 
in the model config (e.g. in the model folder's `tabby_config.yml`).

**⁴** DeepSeek-V4's chat template enables reasoning by default and accepts `enable_thinking`
(boolean, or the equivalent `thinking_mode: chat|thinking`) and `reasoning_effort` (`low`,
`high`, `max`; `low` is the default and `high`/`max` prepend effort prompts to the context) as
template variables, settable per request via the top-level fields or `chat_template_kwargs`.

**⁵** LFM2 models emit a Pythonic tool-call list in `<|tool_call_start|>[...]<|tool_call_end|>`,
which the server's bundled template doesn't explicitly steer the model toward. Point the model at
the included `templates/lfm2.jinja` (`prompt_template: lfm2.jinja`) so fresh-session tool calls
reliably use that format instead of drifting to OpenAI-style JSON.
The template requires parallel tool results in the same order as the corresponding tool calls;
TabbyAPI sorts tool messages by `tool_call_id` before templating, so clients may send them in
any order.

### Built-in web tools (UI client)

The chat client can let the model call tools. Server-side tools live behind
`/v1/tools/*` and are configured in `tools_config.yml` (copy
`tools_config_sample.yml`); the file is watched and reloads without a
restart.

- `web_search` queries a SearXNG instance (`searxng.url`; the instance must
  allow `format=json`). Results are title/URL/snippet only, capped by
  `max_results` and `max_result_chars`. The model may narrow a search with
  `categories` (e.g. `news`, `general`, `social media`; depends on the
  instance) and `time_range` (`day`, `week`, `month`, `year`), both forwarded
  to SearXNG. For news or recent events, ask for `categories=news` with a
  `time_range`; the default `general` category often returns homepages or
  nothing for dated queries.
- `fetch_url` downloads a page by URL and returns extracted text, capped by
  `max_page_chars`. Only public http/https addresses are allowed unless
  `fetch_url.allow_private_urls` is set; redirects are never followed.
- `calculator` and `datetime` run in the browser.
- Custom tools are defined in the Tools section of the settings panel as JSON
  tool specs; an optional `x_tabby_execute` block inside `function` makes the
  browser call an API for the tool (its `headers` can carry that API's key).
  The JSON, key
  included, is stored in the browser's local storage, on the machine that
  runs the chat client, not on the TabbyAPI server.

Both tools are off until enabled in `tools_config.yml`. Endpoints require an
API key like every other endpoint. Tool calls execute after approval unless
auto-approve is on; there is a hard cap of 8 tool rounds per reply.

Security notes: the SearXNG token never leaves the server; search results are
untrusted text (prompt injection is possible — keep approval on); hostnames
are resolved and private ranges rejected before fetching (a hostile hostname
that rebinds mid-request is a residual risk; prefer localhost or a trusted
hostname). With `disable_auth: true`, every local process has full access —
keep auth on and use the key from `api_tokens.yml` (printed at startup, or
`cat api_tokens.yml`, or `python tools/add_api_key.py` to add more).
